# VibeSafe analysis data model

## Goals

- Keep a lightweight, immutable history record for every analysis request.
- Preserve old component analyses instead of overwriting audit history.
- Reuse analysis results when source and analysis configuration are unchanged.
- Summarize only the components selected for a run.
- Support classes, triggers, and LWC bundles now, with more metadata types later.

## Analysis history

`AnalysisRun` is the history record displayed in the analyses list. It stores:

- who requested the analysis and for which Salesforce org;
- the requested scope in `requestSnapshot`;
- component counts by type in `selectedCounts`;
- analyzer, rule-set, and profile versions;
- status, timestamps, progress, overall score, and overall summary;
- a final immutable summary payload in `summarySnapshot`.

The request and final summary remain available even when the user only wants a
high-level historical view. `AnalysisRunItem` provides optional drill-down to
the component results used to calculate that summary.

## Component identity and versions

`Artifact` is the stable identity of a Salesforce component inside one org.
Its `identityKey` is generated by the ingestion adapter from metadata type,
namespace, and full name. This avoids duplicate component rows.

`Artifact` stores the Salesforce metadata ID, type, name, namespace, API
version, and last-modified timestamp. Component inventory can be refreshed from
Salesforce without retrieving or retaining source code.

`ArtifactVersion` stores only a SHA-256 content fingerprint, source size, and
retrieval metadata. Source code is never written to PostgreSQL, object storage,
logs, or analysis-history records. A changed component creates a new fingerprint
version; an unchanged component reuses the existing version.

## Duplicate-analysis handling

`ComponentAnalysisResult` is reusable and is unique by:

1. `artifactVersionId`, representing the exact source;
2. `analysisProfileHash`, representing every input that can change the result.

The profile hash must include analyzer version, rule-set version, enabled rules,
scoring policy, AI data mode, provider/model, and prompt version as applicable.

When a new run includes an unchanged component with the same profile, its
`AnalysisRunItem` references the existing result and receives status `REUSED`.
When source or configuration changes, VibeSafe creates a new result. Previous
runs continue to reference the result they originally used.

## Findings and recommendations

Findings belong to a component result. A deterministic fingerprint based on the
rule, artifact identity, source location, and normalized evidence prevents a
single result from containing duplicates and supports future regression tracking.

AI recommendations are separate from findings. Their uniqueness key includes
the finding, provider, model, prompt version, and input hash, allowing responses
to be reused without confusing them with deterministic evidence.

## Summaries

Run summaries are calculated only from that run's items. A partial selection is
never labeled as the complete org-health score. `AnalysisCategoryScore` stores
the security, performance, governor-limit, maintainability, reliability, test,
accessibility, and architecture breakdown for the run.

An org-level health view will later select the latest valid result for every
current artifact and report analysis coverage alongside the score.

## No-source-retention policy

When a user starts an analysis, VibeSafe retrieves source only for the selected
components. The source is held in a request/job-scoped in-memory map, passed to
the deterministic analyzer or configured AI provider, and discarded when the
job finishes. Prompts, provider traces, application logs, exceptions, and job
payloads must not contain source. Persisted results can contain rule evidence
only when that evidence is explicitly reduced or redacted by the result policy.

## Extension strategy

New metadata types require a new enum value and ingestion/analyzer adapter. The
run, version, result, finding, recommendation, and summary structures remain the
same for objects, fields, flows, workflow rules, Process Builder metadata,
validation rules, permissions, and other Salesforce metadata.
